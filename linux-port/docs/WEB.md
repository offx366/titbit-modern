# Экспериментальный перенос в браузер

В браузере проверены все 70 сцен: фон, модели, освещение, анимации, SeeR-скрипты,
видео, диалоги, курсор, инвентарь и меню по Escape.
Исходный движок исполняется в WebAssembly с SDL2/WebGL. Данные читаются из вашего
`QUEST.ezd`; исходный Windows EXE для исполнения не используется.

## Запуск игры

Из корня проекта:

```sh
nix develop path:.#web --command python3 linux-port/tools/build_web_game.py
python3 linux-port/tools/serve_web.py
```

Откройте `http://127.0.0.1:8000/game.html`, выберите свой `QUEST.ezd`, в поле
«Видеофайлы игры» выберите все 18 AVI из той же копии игры и нажмите «Играть».
Файлы обрабатываются в браузере. Управление мышью, Escape открывает родное меню.
Экран сохраняет пропорции 4:3 и помещается в окно; логические координаты движка
остаются 1024×768, включая прицеливание мышью.
Первая сборка скачивает SDL2 port Emscripten и закреплённый FFmpeg 6.1.1
с проверкой SHA-256; ей нужен доступ к сети.

Журнал обновляется пакетами не чаще раза в 100 мс. Строки накапливаются в памяти
с ограничением 120 тысяч символов; измерение высоты журнала выполняется только
когда он открыт, вне игрового кадра. Это устраняет сотни синхронных перерасчётов
страницы во время загрузки сцены. В сравнительном замере шести переходов между
улицей и подворотней загрузка занимала 3,7–7,9 с до исправления и 16–92 мс после
него; время ходьбы персонажа в эти числа не входит. С открытым журналом проверены
загрузка за 20 мс, ограничение объёма текста и сохранение через родное меню.

Для локальной разработки можно передать архив серверу:

```sh
python3 linux-port/tools/serve_web.py --archive .local/verified-game/QUEST.ezd
```

Тогда `http://127.0.0.1:8000/game.html?local=1` запускается без выбора файлов.
AVI должны лежать рядом с архивом. Сервер слушает только `127.0.0.1` и отдаёт
архив и ролики отдельными маршрутами; они не копируются в сборку.
Для потоков WebAssembly сервер выставляет COOP/COEP.
При статическом хостинге нужен HTTPS (localhost разрешён). Если сервер не
выставляет COOP/COEP, `bootstrap.js` регистрирует `isolation-worker.js` и один раз
перезагружает страницу перед загрузкой движка. Service worker добавляет эти
заголовки к ответам сайта; игровые файлы и сохранения на сервер не отправляются.
При запрете service worker и отсутствии заголовков показывается ошибка запуска.

## Публикация на GitHub Pages

Workflow `.github/workflows/pages.yml` собирает движок через закреплённое
окружение `nix develop .#web`. В pull request он проверяет сборку, аудиопроцессор,
ABI и запуск в Chromium на обычном HTTP-сервере без COOP/COEP, по пути
`/titbit-modern/`. После push в `main` успешная сборка публикуется на Pages.
Ручной `workflow_dispatch` также публикует только ветку `main`.

В Settings → Pages выберите Source: GitHub Actions. После слияния PR первый
push в `main` запускает сборку и деплой; URL появляется в environment
`github-pages` и в результате шага Deploy game. Корневой `index.html` открывает
игру; `game.html` тоже доступен. На первом посещении выполняется одна
автоматическая перезагрузка для включения изоляции.

`tools/package_web.py` копирует только перечисленные файлы браузерного запуска
в отдельный пустой каталог. Build-кэш, исходники, логи и .sav в артефакт не
включаются. По умолчанию QUEST.ezd и AVI также не включаются: пользователь
выбирает файлы из своей копии игры. Слоты сохраняются в IndexedDB этого сайта: локальный сервер
и Pages имеют разные origin; для переноса используйте экспорт/импорт `.sav`.

Собрать такой же каталог локально и проверить статический хостинг:

```sh
nix develop .#web --command python3 linux-port/tools/build_web_game.py
python3 linux-port/tools/package_web.py --out .local/pages
nix develop .#web --command node linux-port/tools/check_web_pages.mjs .local/pages
```

Выходной каталог должен быть пустым. Для нового прогона выберите другой каталог
или удалите содержимое предыдущего. Окружение Nix предоставляет Chromium и
Playwright; браузерная проверка не требует игровых данных.

Чтобы публиковать готовую игру без выбора файлов, добавьте repository secret
`TITBIT_GAME_MAGNET` в Settings → Secrets and variables → Actions. Значение —
magnet-ссылка на вашу копию игры. Затем запустите workflow вручную для `main`
или сделайте push в `main`. Только этот доверенный запуск читает secret;
проверки pull request его не используют. Без secret сохраняется обычный режим.

`prepare_web_assets.py` скачивает данные через aria2, извлекает поддерживаемый
каталог игры или ISO/IMG/CUE/CCD и проверяет SHA-256 всех 19 файлов версии 1.00.
Скачанные установщики не исполняются. Magnet передаётся aria2 через stdin,
не записывается в сайт, Nix derivation или кэш зависимостей. Загрузка требует
доступных пиров; при ошибке или несовпадении файлов публикация останавливается.
Сама ссылка скрыта, но включённые в Pages игровые файлы публичны и доступны
для скачивания всем посетителям. Архивы с неподдерживаемой упаковкой нужно
распаковать или преобразовать перед использованием.

В этом режиме сайт предлагает кнопку «Играть», загружает архив и ролики с
Pages и проверяет их контрольные суммы. Для локальной проверки без torrent:

```sh
python3 linux-port/tools/prepare_web_assets.py --source /путь/к/игре --out .local/game-data
python3 linux-port/tools/package_web.py --out .local/pages-bundled --game-data .local/game-data
nix develop .#web --command node linux-port/tools/check_web_pages.mjs .local/pages-bundled
```

Опубликованные игровые файлы после первой загрузки сохраняются в CacheStorage
браузера отдельно от сохранений. Ключ содержит SHA-256 из манифеста: обновление
движка не заставляет заново скачивать неизменившиеся данные. После перезагрузки
проверяются размер и хеш локальной копии; повреждённый или отсутствующий файл
скачивается повторно. Манифест при запуске страницы проверяется на обновления.
При первой загрузке одновременно скачиваются до трёх роликов.

При запрете локального кэша или нехватке места игра продолжает запускаться
по сети и показывает сообщение под игрой. Очистка данных сайта, приватное окно
или вытеснение данных браузером могут потребовать повторной загрузки. Полностью
офлайн-режим движка не реализован. Ленивое чтение роликов пока не включено:
оригинальные AVI-вызовы синхронные, все выбранные ролики готовы до старта сцены.

Проверка кэша с маленькими фикстурами (оригинальная игра не нужна):

```sh
nix develop .#web --command node linux-port/tools/check_web_assets.mjs .local/pages
```

Она проверяет перезапуск браузера с заблокированной загрузкой файла,
смену хеша, восстановление повреждённой копии и отказ локального хранилища.
Для сайта с данными `check_web_pages.mjs` дополнительно запускает настоящий
движок, перезагружает страницу и снова запускает игру с недоступными сетевыми
игровыми файлами, проверяя отсутствие повторных запросов.

В ручном режиме выберите QUEST.ezd и все 18 AVI из своей копии игры.
Перед запуском проверяется наличие каждого ролика: при неполном выборе
показан список недостающих файлов, выбор остаётся доступным. Это предотвращает
чёрный экран вместо заставки.

После «Играть» воспроизводится штатная последовательность: Бука → VZ Lab →
вступление → главное меню. Ролики можно пропускать щелчком мыши.
«Новая игра» в меню запускает сюжетное вступление, затем первую игровую сцену.
Проверка всех сцен не заменяет полное прохождение всех квестовых веток.

## Сохранения в игре

Escape → «Сохранить игру» → один из шести слотов. Дождитесь сообщения
«Слот N сохранён в браузере» под игровым экраном. После перезапуска страницы
Escape → «Восстановить игру» загружает этот слот штатным сценарием игры.
Раздел «Перенос сохранений» позволяет скачать и импортировать исходный `.sav`.

Перед запуском движка файлы `slot1.sav`…`slot6.sav` восстанавливаются из IndexedDB
в его файловую систему. После закрытия записанного файла снимок 408 байт проходит
через `SaveStore`; подтверждение показывается после завершения транзакции.
Исходные `QuestState::SaveGame`/`LoadGame` и игровые сценарии меню не изменены.
Игровые слоты используют базу `titbit-saves`, диагностический стенд — отдельную базу.
Origin (включая порт) и профиль браузера должны совпадать; очистка данных сайта
удаляет сохранения. Скачанный `.sav` служит переносимой копией.

Проверено 21 октября 2026 в Chromium через Playwright: загрузка первой сцены,
тысячи кадров с анимацией, диалог с Утюгом, Escape и меню сохранения, запись
реального слота, побайтовое восстановление 408 байт после перезапуска страницы
и загрузка этого слота через игровое меню с возвращением в первую сцену.
Отдельно проверены запуск через выбор `QUEST.ezd`, скачивание `.sav` и его импорт.

На полной сборке также проверены подбор монтировки мышью, сохранение подворотни,
перезапуск страницы и загрузка слота с побайтовым совпадением файла и сохранённым
предметом. Сохранение из `lab03.XML` возвращает в лабораторию, локацию 40.

## Устройство игровой сборки

`build_web_game.py` собирает 335 единиц frontend, 333 Wasm-объекта и выбирает
332 модуля для игрового линка. `plan_web_link.py` связывает восстановленные имена
по исходным метаданным. `wasm_rewrite.cpp` согласует физические кадры аргументов
MS x86, поля общих объектов, возврат структур, виртуальные деструкторы и генерирует
158 типизированных SeeR-адаптеров. Для 192 таблиц COMDAT выбирается наибольший
провайдер, исключая 120 неполных вариантов.

Frontend и преобразователи используют LLVM 18; C-модули с `setjmp`/`longjmp`
понижаются LLVM из Emscripten, чтобы совпадал ABI его служебных функций.
Платформа использует pthreads, Wasm exceptions, SDL2 и эмуляцию legacy OpenGL.
Браузерная граница добавляет display lists, создание текстур по старым GL-именам,
пересчёт неполных степеней двойки для mipmaps и адаптацию форматов WebGL.
`patch_web_lighting.py` расширяет эмуляцию OpenGL позиционными источниками,
прожекторами и затуханием. SDK не изменяется: при линковке подключается его
локальная расширенная JS-библиотека. AVI декодирует собранный в Wasm FFmpeg
через тот же VfW/DIB-адаптер, что и Linux-порт, включая цветовой ключ и повторы.
При загрузке двух исходных сценариев исправляются несовместимые поля:
`pornodisk.scv` использует `item_porno_disk`, а `anton_lab3.scv` записывает
правильную локацию 40. Архив и формат сохранений не меняются.
Данные начинаются с адреса 65536: старый CString принимает меньшие адреса за
номера строковых ресурсов Windows.

Браузерный вывод звука использует `web/audio_browser.cpp` и `audio-worklet.js`.
Поток декодирования Audiere копирует PCM в кольцевой буфер общей памяти,
а AudioWorklet читает его в аудиопотоке браузера, без вызовов игрового потока.
Прежний SDL ScriptProcessor обслуживал блоки по 1024 отсчёта в потоке интерфейса;
после кликов наблюдались пропущенные сроки подачи блоков (43–52 мс вместо 21 мс).
Подход с общей памятью описан в [документации Chrome](https://developer.chrome.com/blog/audio-worklet-design-pattern).
Очередь сохраняет контракт WinMM: заголовок получает `DONE` после потребления
его PCM, а не после копирования. Завершённые буферы повторно подаются в порядке
воспроизведения, включая переход через конец массива. Native Linux использует SDL.
Громкость и mute применяются в worklet; при отличающейся частоте контекста
выполняется пересчёт отсчётов. Контекст возобновляется по клику или клавише,
ошибка загрузки аудиомодуля показывается на странице.

Этапы можно повторять отдельно: `--stages platform,link` или `--stages rewrite,link`.
Журналы лежат в `linux-port/build/web/game/logs/`; `--out` меняет каталог сборки.

## Запуск проверок

Проверка PCM-процессора без игровых данных:

```sh
node linux-port/tools/check_web_audio.mjs
```

Проверяются стереоканалы, тишина при опустошении и восстановление очереди,
границы кольца и переполнение 32-битного счётчика, громкость/mute, reset,
пересчёт частоты и закрытие. В полной сборке после замены вывода проверены
клики, четыре последовательных перехода улица ↔ подворотня, сохранение 408 байт
и загрузка после перезапуска страницы: счётчик недостающих PCM-кадров равен нулю.
При блокировке игрового потока на 1,5 с аудиопоток продолжал потреблять PCM.
Это измерение подачи данных, а не оценка качества звука на слух.

Для проверки полной игры с вашим архивом:

```sh
python3 linux-port/tools/prepare_web_qa.py --archive /путь/QUEST.ezd --out .local/web-qa
```

В Playwright MCP выполните `browser_run_code_unsafe` с `filename` полученного
`setup.js`, затем 14 раз `batch.js` (по пять сцен), один раз `scripts.js` и
`report.js`. Сервер игры должен работать на порту 8000 с `--archive`.
Стенд запускает настоящий движок в свежем экземпляре для каждой сцены,
проверяет кадры и компиляцию её сценариев, сохраняет снимки. `scripts.js`
проверяет все 417 сценариев в отдельной вкладке, не вызывая игровых событий.
Звук проверочных вкладок заглушается. Результаты хранятся в `page.titbitQa`;
`report.js` возвращает JSON, оригинальные игровые данные в отчёт не включаются.

Результат 21 октября 2026: 70/70 сцен и 417/417 сценариев без ошибок; отдельно
проверены 72 кадра из 18 AVI с переходами начало → середина → конец → начало,
22 обычных перехода между улицей и подворотней в одном экземпляре движка,
сохранения из подворотни и лаборатории, меню на экране 760×570 при буфере
1024×768. Это проверка работоспособности сцен и ключевых действий, а не
подтверждение прохождения каждой комбинации квестовых флагов.

Из корня проекта:

```sh
nix run path:.#titbit-web-probe
```

Откройте `http://127.0.0.1:8000`. Другой порт: `nix run path:.#titbit-web-probe -- 8080`.
Локальный HTTP-сервер только отдаёт статические файлы; код исполняется в браузере.
Сервер слушает только loopback. Данные игры не нужны и в пакет не включаются.

Отдельная сборка и повторная проверка без браузера:

```sh
nix build path:.#titbit-web-probe -o result-web-probe
nix develop path:.#web --command node \
  result-web-probe/share/titbit-web-probe/check.mjs \
  result-web-probe/share/titbit-web-probe/titbit-probe.wasm
```

Файлы в `result-web-probe/share/titbit-web-probe/` можно отдавать любым статическим
HTTP-сервером. Открывать HTML через `file://` не следует: страница загружает `.wasm`
через `fetch`.

## Отдельный стенд сохранений

После запуска сервера откройте `http://127.0.0.1:8000/save-probe.html`.
Это проверка подсистемы сохранений на синтетическом состоянии, **не игровая сцена**.
Введите число, сохраните его в слот, перезагрузите страницу и нажмите «Загрузить»:
число восстановится. Можно скачать `.sav` и импортировать его обратно.
Три тестовых слота используют отдельную базу `titbit-save-probe`.

Подключены настоящие `QuestState::SaveGame_0041e590` и `LoadGame_0041e5e0`
из `src/lanes/engine41/quest_state.cpp`. Они исполняются в отдельном
`titbit-save-probe.wasm`; исходный формат — ровно 408 байт — сохраняется без изменений.
Модуль имеет только четыре типизированных CRT-импорта: `fopen`, `fwrite`, `fread`,
`fclose`. Это узкий файловый адаптер для сериализатора, не полная файловая система игры.
Конструкторы Wasm вызываются явно один раз до работы с состоянием.

`web/saves.js` предоставляет:

- `SaveStore`: запись, чтение, список и удаление слотов в IndexedDB;
- `importFile` / `exportFile`: исходные байты файла без дополнительных заголовков;
- `createSaveRuntime`: соединение исходного сериализатора с браузерным хранилищем.

Запись делает снимок буфера и атомарно сохраняет данные вместе с SHA-256 и временем.
Успех возвращается после `transaction.oncomplete` с запросом `durability: strict`,
а не после успеха отдельного `put` ([спецификация IndexedDB](https://w3c.github.io/IndexedDB/#transaction-lifecycle)).
Ошибка записи передаётся вызывающему коду; предыдущий слот остаётся нетронутым
при прерывании транзакции. Загрузка проверяет размер и контрольную сумму до изменения
состояния движка. Ошибка доступа к IndexedDB не заменяется временным хранилищем
с ложным сообщением об успешном сохранении.

Контрольная сумма хранится отдельно от исходного файла. При импорте проверяется
размер; у оригинального формата нет добавленной здесь сигнатуры, позволяющей
проверить смысл всех игровых переменных. Совместимость полного прохождения
пока не проверена.

Сохранения привязаны к origin (включая порт) и профилю браузера.
Очистка данных сайта удаляет их; скачанный файл служит переносимой копией.
Игровая сборка открывает хранилище до старта меню и подтверждает запись
после завершения транзакции.

### Проверки сохранений

`save-checks.html` автоматически проверяет 11 сценариев, включая настоящую

побайтовый проход исходного сериализатора. Постоянство IndexedDB проверяется
в браузере, а не этой Node-проверкой.

Проверка 21 октября 2026: все 11 сценариев прошли в Chromium через Playwright MCP.
Отдельно проверены кнопки сохранения/загрузки, закрытие и повторное открытие вкладки,

## Что проверяют изолированные ABI-пробы

Сборка использует Clang/LLVM 18 и `wasm-ld` из зафиксированного Nixpkgs.
Emscripten для этого этапа не требуется: модуль не использует libc, SDL или браузерные
импорты. Frontend сохраняет Microsoft x86 C++ ABI в LLVM IR; отдельный преобразователь
меняет целевую платформу на wasm32 и соглашения вызовов.

| Проверка | Результат локального прогона |
|---|---|
| Размеры классов, виртуальные методы, `stdcall`/`thiscall` | PASS |
| Передача нетривиальных объектов через `inalloca`, возврат значений, деструкторы | PASS |
| Настоящий `vector_geometry.cpp`: пересечение луча с плоскостью | PASS |
| Настоящий `Vcpudeco.c`: арифметика, callbacks с `int` и `double`, стек, пауза/продолжение, ошибочный opcode | PASS |
| Смешанные `varargs`: `int`, `double`, указатель, `int64` | PASS |
| `varargs` между модулями: указатель на функцию/метод, структуры, `va_copy`, рекурсия | PASS |

Пять экспортированных проверок выполняются по 100 раз в Node.js; любая ошибка,
включая `varargs`, завершает проверку с ошибкой. Внутри проверки `varargs` выполняется
цикл из 50 000 косвенных вызовов, чтобы обнаружить накопление буферов на стеке.
Модуль не имеет импортов. Исходный тест `inalloca` также проверяет баланс живых
объектов; проверка Linux ESP отключена только для Wasm (`TITBIT_WASM_PROBE`).

### Формат вариативных вызовов

Нативный LLVM 18-преобразователь `tools/wasm_varargs.cpp` обрабатывает Microsoft IR
до смены целевой платформы. Он заменяет `...` явным указателем на непрерывный буфер
аргументов с шагом, кратным 4 байтам (`ms-x86-packed-v1`). `double` и `int64` занимают
8 байт без дополнительного выравнивания; `byval`-структуры копируются по исходному
размеру x86. `va_start` получает этот указатель, сохраняя возможность SeeR брать
адрес `va_arg`. Переносимый `stdarg.h` явно отмечает чтение слотов как невыровненное.
Буфер выделяется в начале вызывающей функции и переиспользуется в циклах.

Обрабатываются прямые и косвенные вызовы, `invoke`, объявления и определения.
Вариативные символы получают префикс `titbit_va_`: например, `printf` становится
`titbit_va_printf`. Поэтому линковка с Emscripten libc требует явных
адаптеров для упакованных аргументов. Функции вида `vprintf` тоже нуждаются в
адаптации принимаемого `va_list`; текущая проверка не использует libc.
Смешивать исходные x86-вызовы, этот формат и нативный Wasm ABI нельзя.

Проверка между отдельными единицами трансляции включает возврат `double` и структуры,
передачу структуры и указателя на метод с поправкой `this` при множественном
наследовании. Нетипичные `va_arg`-инструкции LLVM, вариативные `inalloca`/
`preallocated`, векторы и `musttail` явно отвергаются с диагностикой.
Отдельные проверки защищают от несовместимого target, опасного `musttail`,
неподдерживаемого `va_arg`, конфликта имён и случайного связывания с обычным `printf`.

SeeR получает небольшие синтетические программы в своём родном байткоде. Это
исполнение оригинального интерпретатора, но не компиляция оригинальных игровых
скриптов. Внешние вызовы выполняются через два явно типизированных адаптера;
игровая сборка дополнительно генерирует адаптеры настоящих callbacks. Переход в неподдерживаемое
управление экземплярами/форками останавливает модуль, а не имитирует успех.

## Аудит исходников

```sh
nix build path:.#titbit-web-objects -o result-web-objects
cat result-web-objects/share/titbit-web-objects/objects/report.json
```

331 модуль из текущих рецептов, включая переносимый C++ runtime, проходит frontend.
327 компилируются в перемещаемые Wasm-объекты. Четыре явно отмечены `needs-port`:

- `src/seer/callasm.c` — динамические x86-вызовы функций;
- `src/lanes/codex/import_veneers.cpp` — ассемблерные переходы к импортам;
- `src/lanes/codex/vorbis_file.c` — управление округлением x87;
- `src/lanes/codex/vorbis_lsp.c` — преобразования через x87.

Непредусмотренная ошибка frontend/backend завершает сборку с ошибкой.
Отчёт явно содержит `playable: false`. Эти объекты **не слинкованы в игру**.
Успешная компиляция не доказывает совместимость `varargs`, исключений, RTTI или
каждого игрового вызова. Linux-платформа SDL/OpenGL/FFmpeg сюда не входит.

## Что остаётся проверить и перенести

Воспроизведение AVI, остальные локации, переходы между ними и полное прохождение.
Сборка `titbit-web-objects` выше остаётся отдельным аудитом исходных рецептов;
игровой линк дополнительно заменяет ассемблерные вызовы типизированными адаптерами
и включает переносимые ветви Vorbis.

## Локальная разработка

```sh
nix develop path:.#web
titbit-web-doctor
python3 linux-port/tools/build_web_probe.py \
  --resource-dir "$TITBIT_CLANG_RESOURCE_DIR"
python3 -m http.server 8000 --bind 127.0.0.1 \
  --directory linux-port/build/web/probe
```

Параметры `--compiler`, `--linker`, `--node` и `--out` позволяют запускать проверки
установленным LLVM. Нужны также нативный C++17-компилятор и LLVM 18 development headers
с `llvm-config`: сборщик автоматически создаёт `wasm-varargs`, используя
`TITBIT_NATIVE_CXX` и `TITBIT_LLVM_CONFIG` (по умолчанию `c++` и `llvm-config`).
Готовый преобразователь можно передать через `--varargs-lowerer /path/to/wasm-varargs`
обоим сборщикам Wasm. Nix-цели собирают его автоматически.
Проверки преобразователя отдельно:

```sh
TITBIT_WASM_VARARGS="$PWD/linux-port/build/web/probe/wasm-varargs" \
  python3 -m unittest discover -s linux-port/tools/tests -p test_wasm_varargs.py -v
```

`compile_ms_ir.py` получил необязательные `--win32-headers`,
`--resource-dir`, `--portable`; обычная Linux-сборка сохраняет прежние значения.

Shell содержит Emscripten с его собственным LLVM, отдельный LLVM 18 для frontend
и IR-преобразователя (с заголовками и `llvm-config`), Binaryen, Node.js, Python,
CMake, Ninja, Make, Autotools, pkg-config, curl, Git и FFmpeg для работы с видео.
Win32-заголовки берутся из MinGW. Нативные SDL/OpenGL-библиотеки хоста не подмешиваются
к Wasm: SDL2 собирается портом Emscripten (`embuilder build sdl2`).

`titbit-web-doctor` проверяет версии инструментов, компилирует C-программу с libc
в WebAssembly через `emcc` и выполняет её в Node.js. Его можно запустить одной командой:

```sh
nix develop path:.#web --command titbit-web-doctor
```

Кэш SDK копируется из Nix в записываемый каталог
`${XDG_CACHE_HOME:-$HOME/.cache}/titbit/<store-name-emscripten>/` при первом входе.
Можно задать собственный `EM_CACHE` до входа в shell. Дополнительные библиотеки
и Emscripten ports собираются туда. Скачивание исходников ports при первом
использовании требует сети.

Для сборки нативного LLVM-преобразователя используйте `$TITBIT_NATIVE_CXX` и
`$TITBIT_LLVM_CONFIG`; для frontend движка — `$TITBIT_CLANG`,
`$TITBIT_CLANG_RESOURCE_DIR` и `$TITBIT_WIN32_HEADERS`.

Проверка прототипа 20 октября 2026: выполнены пять проверок Wasm по 100 раз в Node.js
(включая 5 млн косвенных вариативных вызовов), пять проверок диагностики
преобразователя и повторная компиляция 331/327 модулей со свежими заголовками.
Тот же тест вариативных вызовов прошёл в ELF32 под qemu-i386 без преобразования
в упакованный Wasm ABI. Вычислены Nix derivations с зафиксированными inputs;
обе сборки и проверки повторены из изолированных наборов исходников Nix-целей.
Полный `nix build` здесь не выполнен:
доступ к системному daemon закрыт, скачивание отсутствующих зависимостей блокируется
DNS. После подключения Playwright MCP выполнена проверка страницы в Chromium:
все пять проверок прошли при загрузке и после нажатия «Повторить проверки».
Ошибок исполнения JavaScript/Wasm не обнаружено; в консоли только 404 для
отсутствующего `favicon.ico`.

## Освещение моделей

Движок использует стандартный режим OpenGL `GL_COLOR_MATERIAL`
(`FRONT_AND_BACK`, `AMBIENT_AND_DIFFUSE`). Legacy GL в Emscripten игнорировал
этот флаг и подставлял постоянный ambient-материал 0.2, из-за чего модели
выглядели темнее оригинала. `patch_web_lighting.py` передаёт цвет вершины
в ambient/diffuse освещение при включённом флаге. Фоновые текстуры и
отрисовка без освещения не меняются. Поддержан используемый игрой режим;
произвольные режимы `glColorMaterial` не реализованы.

Проверка компилирует настоящий шейдер и сравнивает пиксели в Chromium
для выключенного освещения, стандартного материала и цветового материала:

```sh
nix develop .#web --command python3 linux-port/tools/check_web_lighting.py
```
